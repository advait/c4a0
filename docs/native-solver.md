# Native solver

Status: implemented, not adopted. Pons (`rust/src/solver.rs`) still produces every label and
suite score. This page is the evidence for deciding whether to switch.

`rust/src/native_solver/` is a clean-room Connect Four solver, written without reading Pascal
Pons's source or blog. Its only contact with Pons is the `c4solver -a` binary used as a black-box
oracle. It reproduces the Pons `-a` scores exactly: per column, from the side to move, a win with
the winner's k-th stone scores 22 - k, a draw scores 0, and a full column is `None` (`-1000` on
the wire). The convention was learned from Pons outputs and is pinned by tests against the
committed suites.

## Data shapes

- `board::Board` is the search position. It holds the mover's stones and all stones as column-major
  bitboards with an empty sentinel bit on top of each column, so every line direction is one shift.
  `key() = occupied + mover` is unique and under 2^49. `From<&Pos>` converts cell by cell through
  `Pos::get`, and property tests check moves, wins and threats against `Pos`.
- `tt::Tt` is the transposition table. It is a power-of-two array of `AtomicU64` slots, and its
  size is a parameter (`--tt-mb`, default 256 MiB). Each slot packs the full 49-bit key, the score
  and a `Lower`/`Upper`/`Exact` tag. A probe never returns another position's bound, and one
  atomic store cannot tear. Every stored score is a true bound on the game value, because every
  search runs to the end of the game. A race between threads therefore costs only speed.
- `search::Searcher` runs negamax with alpha-beta, tightened by the score bounds that follow from
  the stone count and by the table. The root is solved by null-window probes, biased toward 0.
  Moves are ordered by the threats they create, center first. `analyze` returns all seven columns,
  like `c4solver -a`.
- `book::Book` holds the exact score of every canonical non-terminal position at one ply. It is
  generated by this solver (`mise run solver:native:book`, ply 10 by default, or
  `C4NATIVE_BOOK_PLY=8`) and never read from the Pons book. The search returns the book score at
  that ply.
- `parallel::par_map` hands out one item at a time from a shared counter. In `analyze_batch` each
  item is a (position, column) pair, so a batch spreads across positions, a single position spreads
  across its columns, and every worker shares one table.
- `brute` is an exhaustive minimax over `c4r::Pos`. It does no pruning and uses none of the
  `board` code. It scores a win from the winner's stone count, and memoizes only exact values of
  fully expanded positions.

### Contested choices

| Choice | Picked | Alternative | Why |
|---|---|---|---|
| Table entry | full 49-bit key in 8 bytes | partial key plus Chinese-remainder indexing, 5 bytes | No false hits, by construction. That matters more for a correctness oracle than 60% more slots per byte. |
| Parallelism within a position | one work item per root column | Lazy SMP or young-brothers-wait | Simple and exact, and it composes with batch parallelism. It caps a single position at 7 busy threads (see below). |
| Early plies | full ply-10 book (809,464 positions, 7.3 MB), built by this solver | ply 8 (91,295 positions) or ply 12 | Ply 10 builds in 22 min, against 21 min for ply 8, and makes the labeling mix 4.3x faster on one thread (see Performance). Ply 12 holds 5,832,236 positions. A 3,000-position estimate projects 19,818 s on 16 threads under load. The same estimate overshot the real ply-8 and ply-10 builds by 2.1x and 3.7x. |
| Best move in the table | not stored | store the refuting column and try it first | Measured on six ply 4-8 positions, one run each: under 1% fewer nodes and slightly slower. |

## Proof

Two runs of `mise run solver:diff` at `DIFF_PER_PLY=2000` compared 228,041 positions with zero
diffs. Run 2 used seed 2 and the ply-10 book. It compared 114,075 positions in 568 s, with the
same per-bucket shape as run 1 and the same clean checks, including 59,621 brute-force positions.
Its summary and log are in [native-solver/](native-solver/).

Run 1 used seed 1 and the ply-8 book. It compared 113,966 positions in 828 s: 109,091 sampled
positions plus every row of both committed suites. All seven scores matched on every position.
The bar is zero unexplained diffs, and the run had zero diffs of any kind. Both runs were on
2026-11-07. The tables below are run 1.

| Ply bucket | Compared | Agree | Brute-force checked |
|---|---|---|---|
| 0-5 | 3,746 | 3,746 | 0 |
| 6-11 | 17,578 | 17,578 | 0 |
| 12-17 | 20,004 | 20,004 | 0 |
| 18-23 | 19,457 | 19,457 | 6,379 |
| 24-29 | 18,902 | 18,902 | 18,902 |
| 30-35 | 18,546 | 18,546 | 18,546 |
| 36-41 | 15,733 | 15,733 | 15,733 |
| total | 113,966 | 113,966 | 59,560 |

The positions come from these strata. All agree.

| Stratum | Positions | What it targets |
|---|---|---|
| exhaustive | 719 | every canonical position at plies 0-4 |
| walk | 73,363 | uniform walks at every ply 0-41, rejecting game-ending moves |
| full_column | 17,140 | walks that prefer one column until it fills |
| near_terminal | 17,869 | walks stopped where the mover can win or must block |
| suite_dev, suite_test | 2,447 + 2,428 | committed suite rows, also checked against their stored Pons scores |

The sample has 56,271 positions with the first player to move and 57,695 with the second.
67,820 positions have at least one full column.

Three checks are independent of the agreement itself, and all came back clean:

- **Exhaustive minimax.** `brute` reproduced both solvers on all 59,560 positions from ply 22 on.
- **Pons self-consistency.** Pons was asked for the 528,876 child positions of every case. Every
  Pons column score equals minus the best score of the child it leads to, so there were zero
  inconsistent rows.
- **Committed suites.** Live Pons equals the stored suite scores on all 4,875 rows.

The verdicts were proven to fire by planting faults, one run each.

- A Pons wrapper ([fault-pons-wrapper.sh](native-solver/fault-pons-wrapper.sh)) adds one to one
  column at ply 10 and one at ply 30. The run reported exactly two `pons_bug` verdicts
  ([fault-pons-diffs.jsonl](native-solver/fault-pons-diffs.jsonl)). The ply-30 fault was decided
  by brute force. The ply-10 fault was decided by Pons contradicting its own child row while
  native stayed consistent and its column-order, bookless configuration agreed.
- A native build that adds one to a column at plies 10 and 30 reported seven `native_bug`
  verdicts and nothing unexplained
  ([fault-native-diffs.jsonl](native-solver/fault-native-diffs.jsonl)).

No Pons bug and no native bug was found. During development every failure was in a test, never
in the solver.

## Performance

Measured with `c4native bench` on 2026-11-07, on a machine shared with other projects. Each run
records the load average beforehand, and the runs saw 3 to 29. The workload is the seeded walk
positions, uniform per ply 0-41 like the labeling sampler. Sides run interleaved, each run on a
cold table. Every run's 789 or 11,341 rows equal the first run's, so no timed run was wrong or
skipped work. Raw output is in [native-solver/](native-solver/).

789 positions (20 per ply, seed 1), 256 MiB table, 5 runs per side. Values are median (range) and
positions/s:

| Side | Ply-8 book (load 3-14) | Ply-10 book (load 9-24) |
|---|---|---|
| native, 1 thread | 47.66 s (46.49-48.53), 17/s | 10.96 s (10.91-11.02), 72/s |
| native, 8 threads | 6.41 s (6.35-6.69), 123/s | 1.52 s (1.51-1.52), 521/s |
| native, 32 threads | 3.18 s (3.11-3.34), 248/s | 0.69 s (0.68-0.74), 1145/s |
| Pons, 32 processes | 0.57 s (0.54-0.60), 1396/s | 0.55 s (0.54-0.58), 1431/s |

With the ply-10 book on 11,341 positions (300 per ply), a 2 GiB table and 3 runs at load 23-29,
native ran at 1161/s (1129-1182) against 1746/s (1636-1758) for Pons. At that rate the 1M-position
`label --per-ply 24000` job would take about 14 min native and 10 min Pons. That is a projection
from this mix, not a measured label run.

- **Scaling.** 8 threads give 7.2x, so the shared table does not limit scaling. 32 threads give
  15.9x. Other processes held a load average of 9-29, and each position can use at most 7 threads
  (inferred from load and the single-position numbers below, not profiled).
- **Single-thread limiter.** 73% of 1-thread time (8.0 of 11.0 s) is plies 6-11. Inferred from
  the book ply, that is plies 10-11, whose child solves search past the book. With the ply-8 book
  the same bucket was 92%.
- **Hardest position.** With the ply-10 book it is `1060010410` (0-indexed moves, ply 10). Alone on
  a cold table it takes 1.46 s (1.43-1.48) on 1 thread and 0.57 s (0.56-0.58) on 32 threads, 5
  runs each. With the ply-8 book it was `52204610` (ply 8), at 4.21 s and 1.77 s. The empty board
  takes 0.06 s, against 0.07 s for Pons (one run each).
- **Memory.** The table is the only large allocation, plus 7.3 MB of book. Peak RSS was 265 MiB with
  a 256 MiB table and 2,064 MiB with a 2 GiB table. A diff run peaks higher (4,557 MiB with a 2 GiB
  table) from 32 concurrent brute-force memo tables.
- **Book build.** Ply 8 took 1,255 s and ply 10 took 1,337 s, on 32 threads at nice 10, one run
  each.

## Rerun

```sh
mise run solver:native:book        # once; writes native-solver/book-ply10.bin
C4A0_SOLVER=solver/c4solver C4A0_BOOK=solver/7x6.book DIFF_PER_PLY=2000 DIFF_SEED=2 mise run solver:diff
# run 1 used the ply-8 book: C4NATIVE_BOOK_PLY=8 mise run solver:native:book, then DIFF_SEED=1 with
# C4NATIVE_BOOK_PLY=8
rust/target/release/c4native bench --book native-solver/book-ply10.bin --per-ply 20 --runs 5 \
  --threads-list 1,8,32 --pons solver/c4solver --pons-book solver/7x6.book
```

`solver:diff` exits non-zero when any disagreement is unexplained. It writes
`native-solver/diff-seed<S>/summary.json` (counts by ply bucket and stratum), `diffs.jsonl` (one
record per disagreement or failed check, with all evidence) and `cases.tsv` (every case with both
rows).

## Gaps before dropping Pons

- **Not wired in.** `pybridge::label_positions` and `main.py build-suite` still call
  `solver::solve_parallel` (Pons subprocesses). A switch calls
  `native_solver::parallel::analyze_batch` in process, and makes each checkout build or fetch the
  7.3 MB book (22 min to build).
- **Throughput.** Native runs at 0.66x of Pons at 32 threads on the labeling mix. The measured next
  lever is a ply-12 book (5,832,236 positions). The estimate for its build is under 3 h, from an
  estimator that overshot by 2-4x before.
- **One hard position** uses at most 7 threads, one per root column. Lazy SMP helpers sharing the
  table would let a single position use the whole machine.
- **Plies 0-21 have no exhaustive check.** There the evidence is agreement of two independent
  implementations and Pons's self-consistency on every child row. The second native configuration
  runs only on suspect cases. A wrong answer that both solvers produced and both kept
  self-consistent would pass.
- **Book trust.** `Book::load` checks framing and key order, not scores. Scores are checked through
  use, since searches from diff positions at plies 0-9 end at the book ply.
- **Scale.** Two seeds at 2,000 per ply. Diffing a full 24,000-per-ply set (about 1M positions)
  before switching would take roughly 80 min. That is projected linearly from run 2.
