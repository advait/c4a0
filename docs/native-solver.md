# Solver

Status: implemented. `rust/src/native_solver/` labels every position the project stores: the
committed suites (`main.py build-suite`) and training labels for the supervised ceiling
(`main.py label`). It runs in process through `pybridge::label_positions`, on every core, so a
fresh clone needs no external solver, no download and no C++ toolchain.

It is a clean-room Connect Four solver, written without reading Pascal Pons's source or blog.
Pons's solver ([PascalPons/connect4](https://github.com/PascalPons/connect4)) inspired it and
labeled the project until 2026-11-09, and its `c4solver -a` binary was the black-box oracle the
native solver was validated against (see Validation history). Scores keep the Pons `-a`
convention, so stored labels and the metric did not change: per column, from the side to move,
a win with the winner's k-th stone scores 22 - k, a draw scores 0, and a full column is `None`
(`x` in label files, `-1000` from `c4native analyze`).

## Data shapes

- `board::Board` is the search position. It holds the mover's stones and all stones as column-major
  bitboards with an empty sentinel bit on top of each column, so every line direction is one shift.
  `key() = occupied + mover` is unique and under 2^49. `From<&Pos>` converts cell by cell through
  `Pos::get`, and property tests check moves, wins and threats against `Pos`.
- `tt::Tt` is the transposition table. It is a power-of-two array of `AtomicU64` slots, and its
  size is a parameter (`--tt-mb`, default 256 MiB). Each slot packs the full 49-bit key, the score
  and a `Lower`/`Upper`/`Exact` tag. A probe never returns another position's bound, and one
  atomic store cannot tear. Every stored score is a true bound on the game value, because every
  search runs to the end of the game. A race between threads therefore costs only speed.
- `search::Searcher` runs negamax with alpha-beta, tightened by the score bounds that follow from
  the stone count and by the table. The root is solved by null-window probes, biased toward 0.
  Moves are ordered by the threats they create, center first. `analyze` returns all seven columns,
  as `MoveScores`.
- `book::Book` holds the exact score of every canonical non-terminal position at one ply. It is
  generated by this solver (`mise run solver:book`, ply 10 by default, or
  `C4NATIVE_BOOK_PLY=8`) into `native-solver/` (gitignored). The search returns the book score at
  that ply, so the book changes speed, never scores.
- `label::label_moves` is the labeling entry point: it rejects illegal and finished sequences,
  then runs `parallel::analyze_batch` on a shared 1 GiB table.
- `parallel::par_map` hands out one item at a time from a shared counter. In `analyze_batch` each
  item is a (position, column) pair, so a batch spreads across positions, a single position spreads
  across its columns, and every worker shares one table.
- `brute` is an exhaustive minimax over `c4r::Pos`. It does no pruning and uses none of the
  `board` code. It scores a win from the winner's stone count, and memoizes only exact values of
  fully expanded positions.

### Contested choices

| Choice | Picked | Alternative | Why |
|---|---|---|---|
| Table entry | full 49-bit key in 8 bytes | partial key plus Chinese-remainder indexing, 5 bytes | No false hits, by construction. That matters more for a correctness oracle than 60% more slots per byte. |
| Parallelism within a position | one work item per root column | Lazy SMP or young-brothers-wait | Simple and exact, and it composes with batch parallelism. It caps a single position at 7 busy threads (see below). |
| Early plies | full ply-10 book (809,464 positions, 7.3 MB), built by this solver | ply 8 (91,295 positions) or ply 12 | Ply 10 builds in 22 min, against 21 min for ply 8, and makes the labeling mix 4.3x faster on one thread (see Performance). Ply 12 holds 5,832,236 positions. A 3,000-position estimate projects 19,818 s on 16 threads under load. The same estimate overshot the real ply-8 and ply-10 builds by 2.1x and 3.7x. |
| Best move in the table | not stored | store the refuting column and try it first | Measured on six ply 4-8 positions, one run each: under 1% fewer nodes and slightly slower. |

## Labeling cost

The committed suites need no book. On 2026-11-09, `main.py build-suite` relabeled both suites
(2,447 dev and 2,428 test positions) bookless on 32 threads in 8 min 7 s wall time (246 CPU
minutes; load average 2 before, 32 after, on a machine shared with other jobs), and both files
came out byte-identical to the committed ones (`git diff --exit-code src/c4a0/suite`, sha256
unchanged). One run. The first 5% of columns, plies 2-6, took about 3 of each split's 4 minutes;
everything from there on took about one. Through `c4native analyze`, the dev suite alone took
3 min 21 s at load 16-41, and the eight ply 0-1 `OPENINGS` positions took 5 min 35 s (one run
each).

With the ply-10 book the same rebuild takes 2.6 s (dev) and 2.9 s (test) in the book-gated
`suite_test.py`, again byte-identical (one run, 2026-11-09). Rebuilding the book took 21 min 30 s
on 32 threads at load 23-32 and reproduced the recorded sha256 (`7b3cf7c6...6d15`).

A large `main.py label` job needs the ply-10 book; `label` refuses to start without it. The
projection below puts the default 1M-position job at about 14 min with it. Without it, the suite
run above implies about 45 CPU-seconds per position at plies 2-6 (under one on average after
that), which projects to about 10 hours for ply 6 alone at the default 24,000 per ply (not
measured). The book is not checked in: it is 7.3 MB, five times the repository's packed
size, and only ceiling experiments need it.

## Validation history

Before the switch, a differential harness (`c4native diff`, removed with Pons; it is at
`e7d9d47` in git history) compared the native solver with Pons's `c4solver -a` on 228,041
positions over two seeds at 2,000 walks per ply, every ply 0-41, plus every committed suite row:
uniform walks, every canonical position at plies 0-4, positions with full columns and positions
where the mover can win or must block. All seven scores agreed on every position, with zero
disagreements of any kind. Three independent checks were also clean: exhaustive minimax
(`brute`) reproduced both solvers on all 119,181 positions from ply 22 on, Pons was
self-consistent on 1,058,402 child positions, and live Pons equaled the stored suite scores on all
4,875 rows. Planted faults in either solver were caught, so the verdicts fired. The run summaries
and logs are in [native-solver/](native-solver/), dated 2026-11-07.

What still guards correctness: `cargo test` checks the search against brute force on late random
positions and against every committed suite row from ply 20 on, and the book against suite rows
read through it. The book-gated Python tests check the ply 0-1 openings and byte-for-byte suite
rebuilds.

## Performance

The Pons rows are history: they were measured before Pons was removed.

Measured with `c4native bench` on 2026-11-07, on a machine shared with other projects. Each run
records the load average beforehand, and the runs saw 3 to 29. The workload is the seeded walk
positions, uniform per ply 0-41 like the labeling sampler. Sides run interleaved, each run on a
cold table. Every run's 789 or 11,341 rows equal the first run's, so no timed run was wrong or
skipped work. Raw output is in [native-solver/](native-solver/).

789 positions (20 per ply, seed 1), 256 MiB table, 5 runs per side. Values are median (range) and
positions/s:

| Side | Ply-8 book (load 3-14) | Ply-10 book (load 9-24) |
|---|---|---|
| native, 1 thread | 47.66 s (46.49-48.53), 17/s | 10.96 s (10.91-11.02), 72/s |
| native, 8 threads | 6.41 s (6.35-6.69), 123/s | 1.52 s (1.51-1.52), 521/s |
| native, 32 threads | 3.18 s (3.11-3.34), 248/s | 0.69 s (0.68-0.74), 1145/s |
| Pons, 32 processes | 0.57 s (0.54-0.60), 1396/s | 0.55 s (0.54-0.58), 1431/s |

With the ply-10 book on 11,341 positions (300 per ply), a 2 GiB table and 3 runs at load 23-29,
native ran at 1161/s (1129-1182) against 1746/s (1636-1758) for Pons. At that rate the 1M-position
`label --per-ply 24000` job would take about 14 min native and 10 min Pons. That is a projection
from this mix, not a measured label run.

- **Scaling.** 8 threads give 7.2x, so the shared table does not limit scaling. 32 threads give
  15.9x. Other processes held a load average of 9-29, and each position can use at most 7 threads
  (inferred from load and the single-position numbers below, not profiled).
- **Single-thread limiter.** 73% of 1-thread time (8.0 of 11.0 s) is plies 6-11. Inferred from
  the book ply, that is plies 10-11, whose child solves search past the book. With the ply-8 book
  the same bucket was 92%.
- **Hardest position.** With the ply-10 book it is `1060010410` (0-indexed moves, ply 10). Alone on
  a cold table it takes 1.46 s (1.43-1.48) on 1 thread and 0.57 s (0.56-0.58) on 32 threads, 5
  runs each. With the ply-8 book it was `52204610` (ply 8), at 4.21 s and 1.77 s. The empty board
  takes 0.06 s, against 0.07 s for Pons (one run each).
- **Memory.** The table is the only large allocation, plus 7.3 MB of book. Peak RSS was 265 MiB with
  a 256 MiB table and 2,064 MiB with a 2 GiB table.
- **Book build.** Ply 8 took 1,255 s and ply 10 took 1,337 s, on 32 threads at nice 10, one run
  each. The build is reproducible. Rebuilding the ply-8 book with a 1 GiB table instead of 4 GiB
  gave the same sha256 (`ef3c11b8...ce94`), so the scores depend on neither table contents nor
  thread scheduling. The ply-10 book's sha256 is `7b3cf7c6...6d15`.

## Rerun

```sh
mise run suite:build && git diff --exit-code src/c4a0/suite   # bookless; byte-identical suites
mise run solver:book                                          # once; native-solver/book-ply10.bin
rust/target/release/c4native bench --book native-solver/book-ply10.bin --per-ply 20 --runs 5 \
  --threads-list 1,8,32
```

`c4native bench` keeps the walk positions of the old comparison for the same seed
(`native_solver::sample`), so its workload matches the recorded runs.

## Gaps

- **Throughput.** Native ran at 0.66x of Pons at 32 threads on the labeling mix. The measured
  next lever is a ply-12 book (5,832,236 positions). The estimate for its build is under 3 h,
  from an estimator that overshot by 2-4x before.
- **One hard position** uses at most 7 threads, one per root column. Lazy SMP helpers sharing the
  table would let a single position use the whole machine.
- **Plies 0-21 have no exhaustive check.** There the evidence is the historical agreement with
  Pons and the committed suite rows the tests replay.
- **Book trust.** `Book::load` checks framing and key order, not scores. Scores are checked through
  use: the book test reads suite rows through a book, and the book-gated suite rebuild reads every
  early row through the ply-10 book.
